## Summary

Three things firmware needs, each on a rule the language has already:

- **Interrupt handlers:** `[<Interrupt "USART2">] let onUsart2 () = …` is a `unit -> unit` function the compiler exports under the C symbol the runtime's vector table references (`IRQ38_Handler`). The runtime's handlers are weak defaults; a Z# handler is the strong definition. No table is generated by the compiler.
- **State shared with a handler** follows decision 47: a handler is checked as a `share<unit -> unit>` is, so what it reaches must be `Share`. Shared state goes through `Atomic` (moved to Core) and `Spsc<'a>`, a single-producer single-consumer queue in Core that is `Share` by construction: the ring buffer from an interrupt to the main code.
- **`[<NoAlloc>]` and `--no-heap`** (DESIGN §10): a compile error naming the call chain when a function may allocate or free, from one allocation analysis on Z#'s Core after its optimizations; a handler is `NoAlloc` implicitly. **`Cpu`** holds the intrinsics firmware writes in assembly otherwise: `wfi`, fences, masking, and `Cpu.critical` for a compound update.

```fsharp
let rx : Spsc<u8> = Spsc.create 64              // from the handler to the loop: one producer, one consumer
let presses = Atomic.make 0

[<Interrupt "USART2">]                          // IRQ 38 on an STM32F401, from the board's table
let onUsart2 () =
  if Mmio.read32 usartSr &&& bit 5 <> u32 0 then                       // RXNE: a byte waits
    Spsc.push rx (u8 (Mmio.read32 usartDr &&& u32 0xFF)) |> ignore     // false when full: the byte is dropped

[<Interrupt "EXTI15_10">]                       // the button on PC13
let onButton () =
  Mmio.write32 extiPr (bit 13)                                         // clear the pending flag
  Atomic.add presses 1 |> ignore

let main () =
  init ()
  Irq.enable 38
  Irq.enable 40
  while true do
    match Spsc.pop rx with
    | Some c -> handle c
    | None -> Cpu.wfi ()                                               // sleep until an interrupt
  0
```

## Motivation

- **Polling is what exists.** `examples/mcu/nucleo-f401.zs` samples the button and the UART in one loop; a byte that arrives while the loop prints a reply is lost, and the chip never sleeps. The only interrupt in a Z# program today is the runtime's own SysTick, counting wraps for `Runtime.ticks` (`rt-embedded.c` ~381–393 at HEAD).
- **The classic bug** is a handler and the main code touching one variable: a count changed halfway through the main code's `dup`, a record read while the handler writes it. Z# has the rule for this already: what crosses threads must be `Share` (DESIGN §7), and a handler is a thread that preempts the one it shares a stack with. The rule needs no new concept, only a new place to apply it, and two types a handler can share through.
- **Where the heap is touched.** Z# allocates implicitly (strings, closures, boxed unions), and firmware must know where. The report on microcontrollers shows a 4 KB buffer on the heap where C keeps a static array ([the report](../reports/microcontrollers.md)); on a 16 KB part the heap is the RAM budget. Decision 26 chose a checked opt-in over Zig's explicit allocators: `[<NoAlloc>]` names the chain to the allocation, and `--no-heap` builds an image with no heap at all.
- **Assembly.** `wfi` in an idle loop, a fence after a register write, a masked compound update: today they're in the runtime's C or not available. Ten named intrinsics cover what drivers write.

## Detailed design

### Interrupt handlers

```fsharp
[<Interrupt "SysTick">]  let tick () = …          // a core exception, by name
[<Interrupt "USART2">]   let onUsart2 () = …      // a device line, by its name in the board's table
[<Interrupt 38>]         let onUsart2 () = …      // the same line, by number
```

- **Form:** a top-level function of type `unit -> unit`, not generic, with the attribute's one argument a string or a number. The attribute parser takes a string or identifiers today (`Syntax.fs` ~2222–2262 in the main checkout) and gains a number, which 0013's `[<Width n>]` and 0014's `[<Align n>]` need too. One handler per line; a second is an error naming the first.
- **Only in a microcontroller build.** The driver tells the checker the target, as it tells it Std's modules are unavailable (`Driver.fs` ~915, `Typer.fs` ~585 in the main checkout); a host build stops at the attribute with the target in the message.
- **The symbol.** `[<Export>]` is the one attribute that names a symbol today (`Typer.fs` ~3512, the wrapper at `Codegen.fs` ~3962 in the main checkout; facts sheet §5): a wrapper with external linkage and the C calling convention calls the internal `@"zs.<name>"`. `[<Interrupt>]` reuses that path with the symbol from the table below, and `unit -> unit` makes it `define void @IRQ38_Handler()`. On Cortex-M a handler is an ordinary AAPCS function (the hardware stacks the caller-saved registers), so nothing else is emitted.
- **Kept by the linker.** Bare-metal builds link with `--gc-sections` (`Driver.fs` ~1820 in the main checkout), so an exported function nothing references would go. The vector table is `KEEP`'d by `cortex-m.ld` and references every handler's symbol, which is what keeps a handler alive.

| Attribute | Symbol | What the runtime does |
|---|---|---|
| `"NMI"`, `"HardFault"`, `"MemManage"`, `"BusFault"`, `"UsageFault"`, `"SVCall"`, `"DebugMonitor"`, `"PendSV"` | `<Name>_Handler`, CMSIS's names | the runtime's `fault` (a panic) or an empty function is the weak default; the Z# definition replaces it |
| `"SysTick"` | `zs_systick_user` | the runtime keeps `SysTick_Handler`: it counts the wrap for `Runtime.ticks`, then calls `zs_systick_user`, a weak empty function the Z# handler replaces. So the handler runs at the runtime's period (a wrap of the 24-bit counter: about a second at 16 MHz), and `Runtime.ticks` keeps working |
| a number `n` | `IRQ<n>_Handler` | a weak alias of `zs_irq_default` in a table of `ZS_IRQ_COUNT` entries after the 16 core ones |
| a device name | the line's `IRQ<n>_Handler` | the name is looked up in the board's table |
| `"Reset"` | | not allowed: the reset handler is the runtime's startup |

- **The runtime.** Today `vectors[16]` holds the 16 core exceptions, `SysTick_Handler` is `static` and the faults share one function (`rt-embedded.c` ~379–397 at HEAD). After:

```c
__attribute__((weak)) void zs_systick_user(void) {}
void SysTick_Handler(void) { systick_wraps++; zs_systick_user(); }
__attribute__((weak, alias("fault"))) void HardFault_Handler(void);          // and the other core exceptions
void zs_irq_default(void);          // reads the active line from ICSR, disables it, records it for 0016's loop
#define ZS_IRQ(n) __attribute__((weak, alias("zs_irq_default"))) void IRQ##n##_Handler(void);
__attribute__((section(".vectors"), used)) static void *const vectors[16 + ZS_IRQ_COUNT] = { &_estack, Reset_Handler, NMI_Handler, HardFault_Handler, /* … */ SysTick_Handler, IRQ0_Handler, /* … */ };
```

- **`ZS_IRQ_COUNT`** is passed to the runtime's compile as `ZS_HEAP_SIZE` is (`Driver.fs` ~1815 in the main checkout), from the board's table. A number past it is a compile error.
- **The default handler** (`Irq.wait` in [0016](0016-async-bare-metal.md)): disables the line in the NVIC, so an enabled line nobody handles doesn't fire forever, and pushes the number to the loop's `Spsc`, which wakes the task waiting on it. A user handler replaces the default, so `Irq.wait` on that line is a compile error naming the handler.
- **Names.** A device line's name and number are the chip's. `runtime/boards/<board>.irq` lists them as `USART2 = 38` lines, one file per board beside its linker script (item 4's boards bring theirs); an SVD has the same `<interrupt>` elements, so the `svd` provider ([0001](0001-type-providers.md)) can write that file. The QEMU boards' files list their UART and timer lines.
- **`Irq`,** in Core, written in Z# over `Mmio`: `Irq.enable n`, `Irq.disable n`, `Irq.pend n` (the NVIC's set-enable, clear-enable and set-pending registers at `0xE000E100`, `0xE000E180`, `0xE000E200`). `Irq.pend` makes a handler testable under QEMU with no peripheral. 0016 adds `Irq.wait`.
- **What a handler can't do.** It is `[<NoAlloc>]` implicitly (the allocator isn't reentrant, DESIGN §10), its effect row is empty ([0002](0002-effect-handlers.md): there is no handler to resume into), and `Task`, `Mutex` and `Channel` are errors in it and in what it calls: a handler pushes to an `Spsc`, and the program's loop does the rest. A panic in a handler stops the program as any panic does (decision 5).

### State shared with a handler

- **The rule:** a handler is checked as a `share<unit -> unit>` is (decision 47): after monomorphization the compiler follows its calls, and reaching a top-level value that isn't `Share` (a `ref`, a `Buffer`, a closure over one) is an error naming the value, the path and the alternatives. This is `Mono.checkShared`'s walk (`Mono.fs` ~386–498 in the main checkout) with a handler as one more root; its captures are nothing, since a handler is a top-level function.
- **Marking.** The top-level values a handler reaches are marked shared at startup, as they are in a program with threads (DESIGN §7), and a program with a handler is compiled as one with threads: the slow path of `dup` and `drop` has the atomic operations (§7.1), which thread-local objects, most of a program's, never take. On the Cortex-M4 they are `ldrex`/`strex` loops; the Cortex-M0 has no exclusive access, so `rt-embedded.c` provides the `__atomic_*` functions LLVM calls there, each a load and a store with interrupts masked. So a handler never changes a count the main code is changing: it reaches only shared objects, counted atomically, plain values and static objects, which have no count traffic.
- **`Atomic<T>`** moves from Std to Core (`lib/std/Threading/Atomic.zs` today, `lib/core/Threading/Atomic.zs` after; its full name `Threading.Atomic` and its functions `make`, `get`, `set`, `exchange`, `compareExchange`, `add` are unchanged). On the Cortex-M0 each operation masks interrupts around a plain load and store.
- **`Spsc<'a>`,** new in Core beside it: a fixed-capacity queue with one producer and one consumer, `Share` by construction, elements `Share`.

```fsharp
Spsc.create : int -> Spsc<'a>              // the capacity; storage inline, allocated once
Spsc.push   : Spsc<'a> -> 'a -> bool       // from the handler; never waits; false when full
Spsc.pop    : Spsc<'a> -> option<'a>       // from the main code; None when empty
```

  - **Representation:** the elements, a head index the consumer alone writes and a tail index the producer alone writes, so no operation needs an atomic: a push stores the element, then its index; a pop reads the index, then the element. The index stores are volatile, and a `dmb` goes between the element and the index on a target with more than one core, which Z#'s targets don't have.
  - **One handler per queue.** The reach walk finds which handlers reach a queue; two is an error (the queue has one producer). The main code is the other side, whichever direction the values flow: a transmit queue the main code fills and a handler drains is the same type.
  - **Pushing marks** the value's object graph as `Channel.send` does (§7.1): one test for a plain value, a static object or a graph already shared, which is all a handler can hold.
  - **Why not `Channel`:** it waits, locks and allocates, and a handler can't do any of those. `Spsc` is the ring buffer every firmware writes by hand, with the two-sides rule checked. 0016's loop drains one from the default handler.
- **`Cpu.critical (fun () -> …)`** runs its body with interrupts masked (PRIMASK saved, `cpsid i`, the body, PRIMASK restored, so it nests), for a compound update: two `Atomic`s read together, or a sequence the main code must finish before any handler runs. The body is compiled in place (as a lambda that is only called is, DESIGN §9.1) and checked as `[<NoAlloc>]`, so a critical section is short by construction. It returns the body's value: `Cpu.critical : (unit -> 'a) -> 'a`.

| A handler may reach | A handler may not reach |
|---|---|
| plain values it computes, static objects (literals, cases without fields, [0014](0014-placement.md)'s constants in flash), `Mmio` registers | a `ref`, a `Buffer`, a closure over either |
| a top-level `Atomic`, `Spsc`, or any immutable value (a lookup table), marked shared at startup | a `Mutex` or `Channel` (they wait), a `Task` (it allocates and needs the loop) |

### `[<NoAlloc>]` and `--no-heap`

DESIGN §10's paragraph gives the contract: a compile error naming the chain if a function, or anything it calls, may allocate or free heap memory; checked on Z#'s own IR after borrow inference, unboxing and fusion; freeing counts; externs trusted; handlers implicitly `NoAlloc`; `--no-heap` for the whole program. What follows is the analysis that implements it, which [0011](0011-debug-info-profiles-traces.md) shows as hints.

- **Where it runs:** once, after reference counting (`Rc.run`, `Driver.fs` ~1023 in the main checkout) and before IR emission, on the Core every build makes. Z#'s passes don't depend on `-O`, which is clang's flag, so the verdict is the same at `-Os` and `-O2`; `-g` skips inlining and simplification today (`Driver.fs` ~988–993), and the passes run anyway for the functions this check covers, so there is one verdict per program (*Unresolved questions*).
- **Per-site verdicts,** one per Core node that touches the heap:

| Verdict | Site in Core after `Rc` | Counts for `NoAlloc` |
|---|---|---|
| allocates | `CCtor` of a boxed union case with fields (a list cell among them); `CMkClosure` with captured values; a string built (`String.concat`, `String.sub`, an interpolation, `string x`, `Show`); `Array.create`, `init`, `map` and the other array builders; `Buffer.create`, `Spsc.create`, `ref`, `Atomic.make`, `Mutex.make`, `Weak.create`, `dyn` boxing, a `task { }`'s frame and `Task.start` | yes |
| reuses | `CCtorAt` with a reuse token: writes into the matched cell when it was unique, allocates otherwise | yes: the token may be null |
| frees | `CDrop` and `CDropFields` of a value with a heap representation, unless it is static (a literal, a case without fields, a constant in flash) or the compiler knows it's unique and plain | yes |
| copies on write | `CArraySet` on an array that may be shared: the write copies it first | yes |
| atomic | `CDup` or `CDrop` on an object that may be shared: atomic count operations, in a program with threads or handlers | no: no memory moves |

- **What passes:** plain values (numbers, records, tuples, small unions, `option<int>`), static objects, borrowed parameters (a function that only reads its `string` or `list` parameter borrows it and drops nothing, DESIGN §5.2), `Mmio`, `Cpu`, `Irq`, `Atomic`, `Spsc.push` and `pop`, externs, a fused pipeline (no list is built), a panic (its message is static, so bounds and overflow checks pass), and `println` of a literal. So a `NoAlloc` function may hold heap values only borrowed: `putLine (s: string)` passes, `let s = describe mode in putLine s` doesn't when `describe` returns an interpolation.
- **The chain.** Each function's verdict is memoized over the call graph: the first site, or the callee through which one is reached. The error lists the path from the marked function: `reply is [<NoAlloc>], but reply -> describe -> String.concat allocates a string (main.zs:31)`. Generic instances are named without their types, as `checkShared`'s paths are.
- **Calls through closures** whose code the pass can't see count as allocating, and the error names the parameter. After inlining and lambdas applied in place, the higher-order library functions a handler uses (`List.iter` over a constant list, `Option.map`) are first-order by then.
- **Builtins** are classified in the compiler's table (`Typer.builtins`), where `Mmio` and `Runtime.ticks` are; `zs_str_of_i64` allocates in `rt-embedded.c` (~195 at HEAD), so printing a number piece counts until the runtime prints numbers without a string, which the exit test below makes it do.
- **`--no-heap`:** every function, the startup values and `main` are checked as `NoAlloc`; an error names the top-level value or the chain. The runtime is compiled with `-DZS_NO_HEAP`: no heap array, and `zs_alloc` declared but not defined, so a reference left anywhere (a runtime string function the table got wrong, say) fails the link naming its caller, the backstop for the table. The exit report drops its heap fields, and `Runtime.allocations ()` is 0. A top-level `Atomic`, `Spsc` or `Buffer` is placed statically by [0014](0014-placement.md), which a `--no-heap` image needs; until then they are startup allocations the check reports. `heap = 0` in 0014's `[target.<name>]` table means `--no-heap`.

```sh
zs build firmware.zs --target cortex-m0plus --no-heap -Os -o firmware.elf
```

### `Cpu` intrinsics

In Core, `lib/core/Cpu.zs` is a header as `Mmio.zs` is ("its functions are built into the compiler"): the checker's builtin table has them (`Typer.fs` ~279–283 holds `Mmio`'s), and code generation emits each as LLVM inline assembly with a memory clobber (`call void asm sideeffect "wfi", "~{memory}"()`), so no load or store moves across it; `Mmio` accesses are volatile and keep their order anyway.

| Function | Cortex-M | On a host |
|---|---|---|
| `Cpu.nop : unit -> unit` | `nop` | nothing |
| `Cpu.wfi`, `Cpu.wfe`, `Cpu.sev : unit -> unit` | `wfi`, `wfe`, `sev` | nothing: a hosted program waits in `Task` |
| `Cpu.dmb`, `Cpu.dsb : unit -> unit` | `dmb`, `dsb` | a full fence (`fence seq_cst`) |
| `Cpu.isb : unit -> unit` | `isb` | nothing |
| `Cpu.enableInterrupts`, `Cpu.disableInterrupts : unit -> unit` | `cpsie i`, `cpsid i` | a compile error naming the target |
| `Cpu.critical : (unit -> 'a) -> 'a` | `mrs r, primask`; `cpsid i`; the body; `msr primask, r` | a compile error naming the target |

RISC-V (track M item 5) adds a column: `wfi` and `fence` exist, `wfe` and `sev` don't (nothing), and masking is a CSR write. A handler there needs the `mret` return, which the runtime's default entries give; the Z# function is called from them as `zs_systick_user` is.

### Order of implementation

1. **The runtime:** the 16 core handlers as weak defaults, `zs_systick_user`, the `ZS_IRQ_COUNT` table with `zs_irq_default` (`rt-embedded.c` ~379–397 at HEAD), the count from the board's `.irq` file through `Driver.mcus`.
2. **`[<Interrupt>]`:** the number argument in the parser, the checker's case beside `[<Export>]`, the symbol table, the reach check as one more `checkShared` root, `Irq` in Core; `Atomic` to Core with the Cortex-M0 masking; `Spsc` and its one-handler rule.
3. **The allocation analysis,** `[<NoAlloc>]`, implicit on handlers and on `Cpu.critical`'s body; `--no-heap` and `ZS_NO_HEAP`; the runtime printing numbers without a string.
4. **`Cpu.critical`,** needed by the sharing rules; the rest of `Cpu` after phase 11, with item 11.
5. **Board tables** for item 4's boards; RISC-V's entries with item 5.

**Exit tests,** in `tests/mcu/`, built with `--target cortex-m4` and `cortex-m0plus` and run under QEMU as `bench/mcu/run.sh` runs its programs (today `test.sh` ~139 checks `tests/mcu/std.zs` inline, and `--target` means qemu-user):
- `isr.zs`: a handler on a line pended with `Irq.pend`, counting in an `Atomic` and pushing to an `Spsc`; the main code prints both and `Runtime.allocations ()` before and after, equal.
- `systick.zs`: `[<Interrupt "SysTick">]` runs, and `Runtime.ticks` stays monotonic across wraps.
- `err_isr_ref.zs`, `err_isr_task.zs`, `err_noalloc.zs` (`.err`): the three messages below, the last with a three-function chain.
- `noheap.zs` with `--no-heap`: builds, the image has no `zs_alloc` (`llvm-nm`), the report line has no heap fields; the same program with an `Array.init` startup value fails naming it.
- `examples/mcu/nucleo-f401.zs` rewritten on handlers and `wfi`, with its main loop `[<NoAlloc>]`.

## Drawbacks

- **A program with a handler pays the atomic slow path** on shared objects, as a program with threads does: `ldrex`/`strex` on the M4, masking on the M0. Only objects a handler reaches or pushes take it, and a handler that shares `Atomic`s and plain values through an `Spsc` shares nothing counted.
- **The sharing rule is strict.** A handler can't update a record in place, as Rust's `Mutex<RefCell<T>>` lets it; it pushes values and the main code applies them. Programs in that style are restructured, and the restructured form is the one that doesn't mask interrupts around every access.
- **`[<NoAlloc>]` depends on the optimizer's result:** a change in inlining can turn a passing function into an error. A reuse site counts as allocating, so reuse can't be relied on and then lost; and the chain says what changed.
- **SysTick's period is the runtime's.** A SysTick handler isn't a program's tick; a program with its own period uses a timer peripheral's line or 0016's `Task.sleep`.
- **Flash:** the table grows by `ZS_IRQ_COUNT` words (an estimate: under 400 bytes for a chip with under a hundred lines), and the weak defaults a few bytes each.
- **`Cpu` is per architecture,** and `wfe`/`sev` have no RISC-V equivalent; the table says what each target does rather than hiding it.
- **Two ways to not be interrupted,** `Atomic` and `Cpu.critical`; the first is the default and the second is for what the first can't express.

## Alternatives

- **A vector table generated by the compiler,** with handlers placed by it (as TinyGo's and Zig's startup code do): the compiler would own the chip's layout and the startup, which `rt-embedded.c` has; weak defaults in the runtime and the linker's `KEEP` do the same with no code in the compiler. Not chosen.
- **No hidden allocation everywhere** (Zig's explicit allocators): every string, closure and list would take an allocator, in every program; decision 26 chose the checked opt-in, which costs nothing outside firmware.
- **Atomic counts on ISR-shared objects without the Share rule** (let a handler reach anything, counting atomically): a `ref` or a `Buffer` would still race between the handler and the main code; the Share rule is the one threads have, and a handler is a thread that preempts.
- **Rust's `Mutex<RefCell<T>>` in a `critical_section`:** any value shared, every access masked, the main code's too, and a borrow that panics at run time. `Cpu.critical` keeps that form for the compound cases; the queue and the atomics are the default, and they mask nothing on the M4.
- **Inline assembly in Z#** (`asm` blocks, as Rust and Zig): a syntax, register constraints and per-target text in programs; ten intrinsics cover what drivers write, and the runtime's C has `asm` for the rest.
- **Handlers registered at run time** (`Irq.handle 38 (fun () -> …)`): a closure call through a table at interrupt time, captures that must be Share anyway, and nothing for the linker to place; the attribute gives a plain function and a symbol C tools know.
- **A run-time check** (a flag the allocator tests inside a handler): finds the allocation on the device, late; the analysis finds it when compiling and names the chain.

## Compatibility

- **Not breaking.** `[<Interrupt>]` and `[<NoAlloc>]` fail today with `attributes are only supported on type declarations yet` (`Typer.fs` ~3616 in the main checkout); `Cpu`, `Spsc` and `Irq` are new modules, which a program's own would shadow as any; `Atomic` keeps its full name and functions in Core. An older compiler stops at the attribute with that message, and at `--no-heap` as an unknown option.
- **Compiled binaries:** none to consider (packages are source, decision 27). The generated symbols are CMSIS's names, so a vendor's C file beside a Z# program sees the handlers it expects.
- **The library:** `Atomic` moves to Core; `Spsc`, `Cpu` and `Irq` are added there; `Mutex`, `Channel` and `Task` stay where [0016](0016-async-bare-metal.md) and the library's plan put them. A package using `Atomic` builds for a microcontroller after this.
- **Microcontrollers:** the subject. A program without handlers compiles as before; one with a handler is compiled as a program with threads (shared counts atomic). On a host, handlers, `Cpu.critical` and the masking functions are errors naming the target, the fences are fences, and `[<NoAlloc>]` works on every target, for a hot loop that must not allocate on the host either.
- **The runtime's C:** `rt-embedded.c` gains the weak defaults and the device table; a C file that defined `SysTick_Handler` itself conflicted with the runtime's static one before and does now.

## Pragmatics

### Diagnostics

| Situation | Error |
|---|---|
| a handler that isn't `unit -> unit` | `an interrupt handler takes unit and returns unit; onButton is int -> unit` |
| a generic handler | `interrupt handler 'tick' must not be generic; add type annotations` |
| an unknown name | `no interrupt named 'USART9' on this board: the lines are in runtime/boards/nucleo-f401.irq, or give the number: [<Interrupt 38>]` |
| a number past the chip's lines | `IRQ 48 is past this chip's 32 lines (cortex-m0plus, runtime/boards/microbit.irq)` |
| two handlers for one line | `IRQ 38 already has a handler: onUsart2 at main.zs:40` |
| a handler in a host build | `interrupt handlers exist on microcontrollers; this build is for x86-64 (zs build --target cortex-m4)` |
| a handler reaching state it can't share | `interrupt handler 'onButton' uses the top-level value 'count' : ref<int>, which a handler can't share with the program: count in an Atomic, or push through an Spsc` |
| `Task`, `Mutex` or `Channel` in a handler | `'Task.start' can't run in an interrupt handler (onUsart2 -> notify): push to an Spsc, and let the program's loop do the rest` |
| a handler that allocates | `interrupt handler 'onUsart2' allocates: onUsart2 -> describe -> String.concat allocates a string (main.zs:31)` |
| `[<NoAlloc>]` violated | `reply is [<NoAlloc>], but reply -> describe -> String.concat allocates a string (main.zs:31)` |
| a `NoAlloc` function that frees | `step is [<NoAlloc>], but it drops 'old' : list<Event>, which may free its cells; borrow it, or keep it alive in the caller` |
| a `NoAlloc` function calling a closure it can't see | `step is [<NoAlloc>], but it calls 'f', a function parameter, whose code the check can't see` |
| `--no-heap` with a startup value | `--no-heap: the top-level value 'table' allocates at startup (Array.init); make it a constant, or place it statically ([<Section>])` |
| two handlers reach one `Spsc` | `two handlers reach 'rx' : Spsc<u8> (onUsart2, onTimer): an Spsc has one producer; give each handler its own queue` |
| `Irq.wait` on a handled line | `Irq.wait 38 can't be used: IRQ 38 has a handler (onUsart2), which runs instead of the loop's` |
| `Cpu.critical` with a body that allocates | `Cpu.critical's body runs with interrupts masked and must not allocate: it calls List.map, which allocates a list` |
| `Cpu.disableInterrupts` on a host | `Cpu.disableInterrupts exists on microcontrollers; this build is for x86-64` |
| a full queue | none: `Spsc.push` returns `false`, and the handler decides |

### Tooling

- **`zs lsp`:** hover on a handler shows `onUsart2 : unit -> unit` and `interrupt handler: USART2 (IRQ 38), symbol IRQ38_Handler, NoAlloc`; on a `[<NoAlloc>]` function, its verdict or its chain; definition on the attribute's name opens the board file's line; completion lists `Cpu.`, `Spsc.`, `Irq.` and `Atomic.` members as any module's. Diagnostics while editing: the form, the host target and `Task` in a handler come from the checker, with no build run. The reach and allocation verdicts come from the passes after monomorphization, which today run only in a build (`Driver.check` is the checker alone, `Mono.checkShared` runs in `lift`, `Driver.fs` ~947 and ~991): the server runs them to reference counting, with no IR, for a program with handlers or `NoAlloc` functions, which bare-metal programs (one module, small) keep inside track E's budget; the per-site verdicts are the hints [0011](0011-debug-info-profiles-traces.md) shows.
- **The grammar** gains a number as an attribute argument (`grammar.js` ~84–87 takes a string or identifiers), pinned for Zed as grammar changes are.
- **Commands:** `zs build --no-heap`; `zs doc` documents `Cpu`, `Spsc`, `Irq` and Core's `Atomic`; `zs mcp`'s `check` returns the same diagnostics.
- **Debugging:** a handler is a plain function, so gdb through QEMU's stub ([0011](0011-debug-info-profiles-traces.md)) breaks in it, and a fault's handler is named in the backtrace. `ZS_STATS=1` prints the runtime's allocation counters; `Runtime.allocations ()` in a test shows a loop that allocates nothing.

### Performance

- **Existing code:** none on hosts; on a microcontroller a program without handlers compiles as before. With a handler, the slow path of `dup` and `drop` gains the atomic operations, taken only for shared objects; the M0's masking is a few instructions around each (an estimate).
- **A handler:** an ordinary function entered by the hardware; a device line's symbol is the vector entry itself, SysTick's costs one call from the runtime's handler.
- **`Spsc`:** a push or pop is a load, a store, a compare and an index store, no atomic and no wait. **`Atomic`:** one exclusive-access loop on the M4, a masked load and store on the M0. **`Cpu`:** one instruction each; `critical` three around its body.
- **The analysis:** one memoized walk per function after reference counting, linear in the program; `--no-heap` is the same walk over all of it. Nothing at run time.

### Scaling

| Dimension | Typical | Upper bound |
|---|---|---|
| handlers per program | 2–10 | the chip's lines: 32 on ARMv6-M, 496 on ARMv7-M (the architecture's limits); the table is `ZS_IRQ_COUNT` words of flash |
| functions reached by one handler | 5–20 | 1,000, walked once and memoized across handlers |
| functions under `[<NoAlloc>]` | 10–100 | the whole program under `--no-heap`, one walk |
| `Spsc` capacity | 16–256 | 65,536, bounded by RAM: elements inline plus two indices |
| `Atomic`s a handler touches | 1–4 | 100 |
| a `Cpu.critical` body | a few instructions | its length is the interrupt latency it adds; `NoAlloc` keeps it to code with no calls into the allocator, and the guide says to keep it short |

### Culture-aware formatting and parsing

None. Numbers in `.irq` files are decimal, and the messages print numbers as `Show` does (invariant).

## Unresolved questions

1. **The IRQ count per chip:** `ZS_IRQ_COUNT` from the board's `.irq` file (this document). The alternative is the architecture's maximum per target (32 on ARMv6-M, 496 on ARMv7-M) at the cost of flash, so any number works on any board.
2. **`Cpu.critical` nesting:** nests, by saving and restoring PRIMASK (this document). The alternative is an error when nested, which needs a count at run time and gains nothing the restore doesn't.
3. **SysTick ownership:** the runtime keeps SysTick's reload, for `Runtime.ticks` and 0016's timers, and a program's SysTick handler runs at that period (this document). The alternative lets a handler set the reload (`Cpu.systick n`) with `Runtime.ticks` accumulating across changes.
4. **`-g` builds:** the passes that decide allocation run for the checked functions even at `-g`, so there is one verdict (this document). The alternative: `-g` may report an allocation `-O2` doesn't, with the error saying so.
5. **Calls through closures in `NoAlloc` code:** count as allocating (this document). A `noalloc<F>` function type would carry the guarantee as `share<F>` carries Share, at the cost of a fifth function kind, which the third design review's "how many kinds" question weighs.
6. **Where names come from:** board `.irq` files (this document), or the SVD provider alone ([0001](0001-type-providers.md)), which would make every build need the SVD.
7. **Priorities:** not proposed; `Mmio` writes to the NVIC's priority registers work. Whether the attribute takes one (`[<Interrupt("USART2", priority = 2)>]`) waits for a program that needs it.
8. **A second core** (the RP2040 has two): outside this document; 0016 keeps bare metal without threads, and the `Spsc`'s `dmb` is the one place that would change.
